以下金額都是「如果沒發生就能省下」的上限，不是每一筆都省得掉：有些大檔本來就得讀。

可疑浪費的種類

cache 重建的原因取自 Claude Code 記錄的 cache_miss_reason；舊 transcript 沒有這個欄位，原因從間隔與 model 推測，標「推測」。

每一種怎麼算、怎麼避免

cache 重建
上一則的 cache 已經找不到（多半是閒置超過 TTL，Claude Code 用 1 小時），或 model、system prompt 變了，整段 context 要重新寫入 cache，以寫入價計。避免：離開前把進度寫成 handoff 檔，回來開新 session 讀檔接手；session 中途不換 model。
大型 tool 輸出
單次 tool 結果至少 5,000 tokens。它之後每個呼叫都會以 cache read 再付一次，所以算的是「大小 × 之後被帶著的呼叫數」。避免：用 offset/limit、grep、head 讀需要的段落，或把大量閱讀交給 subagent，只收摘要。
重複讀同一檔
同一檔同一段再讀一次，中間沒有改過它。
失敗後原樣重試
tool 回報錯誤後，下一個呼叫用一模一樣的參數再跑一次。

最貴的 400 筆

「之後被帶著」是這筆內容進入 context 後，同一段 context 裡還有幾次呼叫。

哪些 session 最不值得

標記是規則算的：花費至少 $1 卻沒有任何 edit、commit 或 artifact（Agent SDK 除外）是「高花費無產出」；中斷加糾正至少 3 次是「多次糾正或中斷」；花費至少 $0.5 且可疑浪費佔 30% 以上是「浪費比例高」。糾正是用關鍵字抓的，次數會灌水，判讀引用它時要打折。

所有 session

LLM 判讀還沒跑，判讀欄位先隱藏。

方法與限制

  • 花費是 API 等價，對過兩次帳。每個 API 呼叫的 usage 乘上官方單價。跟 Claude Code 自己記錄的 totalCostUSD 比，— 個 session 的中位數比值是 —；跟 ccusage 比，— 在 — 個完整日（到 —）是 — 對 —，比值 —。Max 訂閱額度怎麼換算沒有公開，所以這不等於你用掉多少額度。
  • 這裡只看浪費。每日趨勢與按 model、session 的成本總表用 ccusage（npx ccusage@20.0.42 daily）；當下 session 的固定開銷（system prompt、tool 定義、skill 清單）用 Claude Code 的 /context，它是精確值。
  • 資料範圍。從 — 起，涵蓋 — 條 chain、— 次 API 呼叫；三台的 transcript 保留天數已改成 365 天。claude.ai 網頁對話與雲端 session 不在內。
  • tokens 怎麼分給每筆內容。兩次呼叫之間 context 增加的 tokens（扣掉上一次的 output），依字元數比例分給這段時間插入的 tool 結果、使用者訊息與 attachment。
  • cache 重建的判定。一次呼叫的 cache write 至少 20,000 tokens 且超過該次 context 的一半；金額是重寫的 tokens 乘上（寫入單價 − 讀取單價）。
  • 判讀。花費 $1 以上的 session 都交給 Claude Opus 5.5 讀摘要，判斷值不值得；它只看到節錄，不是整段對話。單次判讀在兩種結果的邊界上會跳，所以每個 session 判 3 次，每次打亂順序重新分批，取中位數。「票數」是跟最終判讀相同的票數，1/3 表示三種判讀各一票，取「部分值得」。標記是規則粗篩的結果，只給判讀當參考。
